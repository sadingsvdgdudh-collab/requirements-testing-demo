# 模块拆分

模块按用户能理解的业务职责划分，例如商品管理、订单管理。跨模块条件可以复制给多个目标，但不能在复制时改写。为每个模块分配全项目唯一的 2–4 位大写字母缩写；编号规则见 [numbering-rules.md](numbering-rules.md)。

## 目录与清单

项目原件和不可变解析底稿放 `input/`。拆分结果放 `output/{模块}/解析.md`，图片放各模块的 `images/`。清单固定为 `output/_公共/拆分清单.json`，所有 `path` 按 `output/` 根目录解析。

```json
{
  "schema_version": "1.0",
  "modules": [
    {"name": "商品管理", "code": "PRO", "path": "商品管理/解析.md"}
  ],
  "sources": [
    {
      "path": "../input/新增商品.md",
      "segments": [
        {"lines": [1, 4], "targets": ["商品管理/解析.md"]}
      ]
    }
  ]
}
```

示例行范围应按真实底稿替换。`lines` 是从 1 开始、含首尾的范围。每个非空源行至少被一个有效 segment 覆盖；每个 segment 的全部原文出现在各 target 内。图片路径可以因复制发生变化，但图片标题、文件名和原文业务描述要保留。清单目标不能越出 `output/`。

同一段原文含多个模块时可以复制原段，再在各模块的规范中说明职责；保留全文上下文比把条件剪散更可靠。尚未归属的业务内容保留到一个明确命名的待归属模块，在规范中说明，不丢弃。

## 交叉依赖

在需求规范“依赖与关联”中列出上游输入、下游可见结果、共享状态及相邻模块 REQ 引用。尚无编号的依赖先按原文记录，不能创造不存在的模块或接口规则。

附图必须随依赖段一并保留，或明确引用到可定位的来源。图中的箭头或布局可以提示关联，不能独自证明未写出的时序、权限或异常规则。

## 检查与报告

执行 `check_split.py --root 项目/output`，根据未覆盖行、越界范围、缺失目标或原文不一致逐项修复。清单应体现真实拆分，不通过扩大范围掩盖遗漏。

在 `output/_公共/拆分报告.md` 记录源文件、模块及缩写、检查结果、重复引用的跨模块段落、人工核对范围和待处理问题。单模块同样运行这一步。检查成功证明源段有去向，不证明需求理解正确。
