# 框架能力、评审版本与执行准备（v1.3）

前 13 列和 JSON `schema_version: "1.0"` 保持兼容。新增元数据只进入 JSON 与报告；评审副本仍只在第 14 列追加 `AI评审`。能力、设计通过、执行准备、测试执行结果分别判断。

## 自动化建议

自动化建议为八值枚举，顺序为：`UI自动化可用`、`UI自动化可做，需采集新资产`、`仅api自动化可用`、`双通道均可用`、`不建议自动化`、`本项目尚无自动化框架`、`当前框架能力不足`、`待核对框架能力`。

- `当前框架能力不足`：已有框架，但缺少本条需要的动作、观察接口、状态准备或时钟控制；`是否可自动化=待定`。明细必须含`理由：`、`缺失能力：`和`补齐办法：`，写清补齐办法。缺数据库接口不能写成仅缺截图。
- `待核对框架能力`：尚未核对路径、函数或资产；`是否可自动化=待定`。明细含`理由：`、`待核对能力：`和`核对办法：`。不凭框架名称、README 宣称具体能力存在。
- 其他六项保留原义。不建议自动化仍仅用于依赖人工主观判断，且与`是否可自动化=否`同时出现。客观规则缺少接口时使用能力不足，不当作主观判断。
- UI 自动化可用和双通道均可用须引用现有函数和场景资产；UI 需新资产引用现有函数并列出待采集文件路径。缺场景资产与缺函数/接口分开，不用新增截图掩盖其它缺口。

## 可核验的能力清单

在模块、其 output 父目录或项目根目录保留`框架能力清单.json`。根目录是本机配置，不复制框架或运行它：

```json
{
  "schema_version": "1.0",
  "framework_root": "实际框架根目录",
  "reviewer": "实际核对者",
  "checked_at": "2026-10-08",
  "capabilities": [
    {
      "id": "UI_SAY",
      "kind": "function",
      "file": "src/gameqa/stendhal_ui.py",
      "symbol": "StendhalUI.say",
      "sha256": "实际文件的完整64位SHA-256",
      "notes": "核对真实聊天输入、客户端命令解析及相应限制。"
    },
    {
      "id": "SEND_BUTTON",
      "kind": "asset",
      "file": "assets/stendhal/send.png",
      "sha256": "实际文件的完整64位SHA-256",
      "notes": "原客户端与分辨率对应的现有发送按钮图。"
    }
  ]
}
```

例中的路径只演示真实核对格式，不是任何项目都具有这些资源。填写实际完整摘要；占位文本不能通过校验。`framework_root`可为绝对路径或相对模块的路径，相对路径不含`..`；环境变量`QA_FRAMEWORK_ROOT`可以覆盖本机位置，清单中的相对能力路径及摘要仍须吻合。能力文件只允许框架根内相对路径，符号链接不能逃出根目录。

用例通过`"automation_evidence": ["UI_SAY", "SEND_BUTTON"]`关联能力编号。校验器检查文件真实存在、完整摘要、Python AST 中实际定义的函数及类方法，拒绝未知编号、伪造函数、丢失文件和摘要变化。不导入或执行框架。其它语言的函数定义目前保留未核验，不能因此标自动化就绪；可引用框架中的真实 Python 入口，并由评审核实动作/观察的数据流。

引用存在不证明函数适合当前场景、截图已校准或脚本能成功运行；这些仍需要具体评审和准备证据。旧数据未填结构化引用时可以读取，但自由文本只视为声明，计算出的能力验证和自动化就绪均不成立。新增用例应填能力引用；缺能力或尚未核对时如实选择对应分类。

## 新评审必须绑定被评审版本

先运行新表单入口：

```text
python3 modules/testcase-builder/scripts/prepare_review.py --module-dir 项目/output/模块
```

它创建新的`评审待填写.json`，包含当前`reviewed_source`、`draft=true`和空的逐条/范围/方法评审。已有输出不覆盖；不会将旧结论补签为新评审。真正阅读当前需求、用例、能力与准备事项后填写 reviewer、逐条结论、全部范围/方法判断，将 draft 明确设为 false，再执行：

```text
python3 modules/testcase-builder/scripts/update_review.py --module-dir 项目/output/模块 --review 项目/output/模块/评审待填写.json
```

评审指纹绑定 REQ、用例设计内容、实际来源/图片/转录、能力清单及被引用框架文件。改预期但保留编号、改业务规则、改来源或能力文件都会使旧评审失效；调整 JSON 缩进或填写实际结果/脚本记录不冒充设计变更。改变准备项也要复核评审，不能给已有结论自动重签。

旧无指纹评审可以作为历史资料保留，不能直接发布。须重新生成待填写表并完成实际评审。设计字段、证据编号、准备项是被评审事实，不因校验失败而删除这些字段绕过门禁。

发布前重新核对输入；任何源工作簿、需求、用例或评审发生变化，临时工作簿拒绝发布。派生输出不得覆盖业务输入。

## 关联编号门禁（先于覆盖）

引用一个不存在的编号不是"覆盖"，而是错误关联。编号存在性在 JSON 侧由 `validate_cases`（REQ/AC）与 `check_traceability.py`（测试点）把关，它们都要求模块里有 `用例数据.json`；**只看工作簿时这两道校验不会执行**，必须补跑：

```text
python3 modules/testcase-builder/scripts/check_workbook_links.py --module-dir 项目/output/模块 --input 项目/output/模块/详细用例.xlsx
```

它读 13＋1 列工作簿与 `追溯` 派生表，逐条核对编号存在与归属，发现问题时以非零退出码结束。`compare_designs.py` 同样核对候选编号，默认拒绝存在假编号的候选，只在 `--allow-link-issues` 时继续并在报告首节标为不通过。

区分三件事，不能互相替代：**编号存在**（本门禁）、**关联语义正确**（逐条核对用例是否真在验证该 AC）、**内容覆盖**（该 AC 是否确实有用例）。编号齐全不代表后两者成立；实测有设计引用了 16 个不存在的 AC 编号、32 个不存在的测试点编号，按引用条数统计仍显示 100% 覆盖。

## 两种关联覆盖

同时报告：全部用例的 REQ/AC 关联覆盖、仅设计评审通过用例的 REQ/AC 关联覆盖。两者使用同一 active 分母；blocked/deprecated 仍排除并说明。需确认、不通过和未评审用例不贡献通过覆盖。

`用例覆盖矩阵.md`逐 REQ/AC 列出全部、通过、需确认、不通过与未评审 TC。`only_unapproved`表示已有设计但没有通过用例支撑，不能与根本未设计的`uncovered`混淆。

`check_coverage.py`默认使用当前有效的`评审结果.json`；没有结果时全部用例覆盖仍可核对，通过用例集合为空并在矩阵中标未评审。也可显式传`--review`选择已绑定版本的评审。过期或无指纹评审不计入通过覆盖。

任何关联覆盖均不是软件执行覆盖、测试充分性或测试通过证明。

## 可行动的准备项

用例 JSON 增加可选`preparation`数组：

```json
{
  "preparation": [
    {
      "id": "PREP_SUPPORT_CLOCK",
      "category": "状态准备",
      "description": "缺少精确support接收时刻与lastMsg控制。",
      "action": "在隔离测试环境补受控服务端时钟，记录同处罚状态下成功T0与本次接收时刻。",
      "status": "open",
      "affects": ["manual", "automation"],
      "resolution": ""
    }
  ]
}
```

category 为`业务规则`、`账号`、`状态准备`、`资产`、`观测接口`；时钟归状态准备。status 为 open/resolved；resolved 必须有具体 resolution。affects 表示影响 manual、automation 或两者，不能从自由文本关键词自动推断。同一 id 可以被多用例共享，但定义、状态和解答须一致。

只有实际核对过准备情况且无缺口，才填`preparation: []`；缺少字段表示准备未核验，不能默认就绪。资产缺口可仅影响 automation；业务规则、未知账号或缺关键观测通常影响两个通道，按真实情况判定。

发布生成`执行准备数据.json`与`执行准备清单.md`，按五类汇总补齐办法及受影响 TC/REQ/AC；相同准备项合并，不重复堆叠逐条解释。

分别统计设计评审通过、人工执行准备就绪、框架能力已核验、场景能力准备就绪、自动化准备就绪和已有执行记录。自动化就绪还要求`是否可自动化=是`、已核对能力、无相应 open 准备项及允许目录内的本地脚本文件；文件存在不证明脚本正确。工作簿中允许人工填写的实际结果与脚本位置也会纳入准备报告；设计指纹仍不受这两项记录变更影响。非空实际结果只表示有记录，不从自由文本推定游戏测试通过。本技能仍不运行被测系统。
