# 用例模板

字段和合法值统一见 [公共数据契约](../../req-processor/references/data-contract.md)。用例编号遵循 [编号规则](../../req-processor/references/numbering-rules.md)。JSON 是内容数据源，Excel 是便于执行记录的输出。

## 固定前 13 列

| 列 | 写什么 | 示例 |
| --- | --- | --- |
| 用例编号 | 稳定唯一 TC | TC_PRO_001 |
| 优先级 | P0/P1/P2/P3 | P1 |
| 用例名称 | 场景与验证目的 | 名称为空时保存 |
| 前置条件 | 角色、位置、初始状态 | 已登录后台，打开新增商品页 |
| 操作步骤 | 按顺序的动作 | 保持名称为空；输入价格99；点击保存 |
| 测试数据 | 具体值/明确数据状态 | 名称为空；价格99 |
| 预期结果 | 可观察业务结果 | 提示名称必填；商品未创建 |
| 实际结果 | 执行后填写 | 未执行则空 |
| 关联需求 | 真正被验证的 REQ | REQ_PRO_001 |
| 是否可自动化 | 是/否/待定 | 是 |
| 自动化建议 | 八值枚举 | 仅api自动化可用 |
| 自动化建议明细 | 判定理由＋已有函数/资源（或需采集的新资产及路径） | 见公共数据契约 |
| 自动化脚本 | 已有脚本位置 | 没有则空 |

第 14 列只在评审副本中追加，名称为 `AI评审`。AC、场景类型、设计方法仅存 JSON，不加入前 13 列；它们供关联检查及评审使用。

工作簿另含 `追溯` 工作表（固定第 2 张），由 `render_xlsx.py` 从 JSON 派生，逐条列出用例编号、优先级、关联需求、验收标准、场景类型、设计方法与关联测试点：

- 目的是让**单独交付工作簿**时这些关联仍可读出。没有它，收件人无法区分"未登记"与"登记为空"，会把已挂 AC/测试点的设计误判成没有关联。
- 它是只读派生视图：不写回 JSON，不参与用例表校验，也不是新的数据来源。前 13 列契约、第 14 列位置与 `read_xlsx` 的首选表逻辑都不受影响。
- 空值按 `未登记` 呈现；`--draft` 生成时按 `未核验（草稿）` 呈现。

## 字段写法

同一批用例里，只有本用例独有的信息写进"前置条件"；测试环境、账号命名、取证方式这类每条都要用的内容写进公共段（见下节），不在每条里重复展开。可读性是硬要求：写完自查一遍，`case_readability.py` 会把不达标项报出来。

| 列 | 写法 |
| --- | --- |
| 前置条件 | 一行一条，只写本条独有的账号、状态、前置关系。不重复公共段，不写取证手段，不出现"已核实""已确认"这类审计措辞（能力是否核对由 JSON 的 `automation_evidence` 表达）。单句不超过 60 字。 |
| 操作步骤 | 一行一个动作，用执行者能照着做的说法。桥接、事件批次、队列长度、探针这类实现细节放公共段或备注，不逐条重复。 |
| 测试数据 | 具体值；阈值、时钟、计数类必须写成可观测的机器可读形式（如 `间隔=59999ms`、`容量=12`），不写"约""若干"。 |
| 预期结果 | 每条都要有落点：在哪个界面、面板、列表、记录、通道或状态字段上看到什么算通过。禁止"正确""正常""符合预期"这类无法核对的表述。 |
| 自动化建议明细 | 按取值保留规定段落；只写实际核对过的能力，不写框架名或 README 声称的能力。 |

术语要求：不直接使用项目内部标识符（如 `openInvites`、`lastMsg`、`PRIVATE_CHAT`）作为描述语言。必须出现时，在模块的术语对照里给出中文说法并在用例中引用；无法翻译的保留原样并加一句解释。不写未完成的句子（如"当前框架尚未封装"），要么说清缺失什么、怎么补，要么移入 `preparation`。

`case_readability.py` 的阈值集中定义在其 `THRESHOLDS` 中，与本表保持一致：

| 阈值键 | 含义 | 默认 |
| --- | --- | --- |
| `unique_ratio_min` | 前置独有信息占比下限（模块内重复片段不计入独有信息） | 70% |
| `max_sentence_chars` | 前置最长单句字数上限 | 60 字 |
| `expected_anchor_rate_min` | 预期结果提到观察对象的比例下限 | 80% |

## 公共段（module_preconditions / evidence_setup）

模块级公共前置与取证方式写在 `用例数据.json` 顶层，只写一次：

```json
{
  "schema_version": "1.0",
  "module": "商品管理",
  "code": "PRO",
  "module_preconditions": [
    "隔离测试服，各用例独立重置账号状态。",
    "A=qaplayer（操作号）、B=qaplayera（接收号）、C=qaobserver（观察号）。"
  ],
  "evidence_setup": [
    "事件取证：各观察端独立消费事件队列并保存批次，队列上限100条，长等待期间持续读取。"
  ],
  "cases": []
}
```

渲染时工作簿新增两份说明工作表「公共前置条件」「取证要求」，并把两段合并成"合并前置条件"追加在工作表末尾的「合并前置条件」列——**原「前置条件」列内容一字不改**，所以旧资料与既有工作簿保持兼容。两个字段缺省即视为未登记，校验器只提示不阻断。

## 提交给脚本前

确认每条步骤可操作、每条预期可判断，输入值与前置状态足以复现。所有 13 个字段都在；实际结果和自动化脚本以外的字段不空。每条用例有 active REQ 与其所属 AC，没有重复 TC 或重复关联。

关联数组不重复，元数据与用例的实际设计一致。用户尚未确认的文案、精度上限或特殊行为不出现在正式预期。设计中的人工建议写待确认事项，不伪装成已经执行的实际结果。

默认 `render_xlsx.py --module-dir 模块目录` 从 `用例数据.json` 读取并生成 `详细用例.xlsx`；`--cases`/`--output` 用于用户指定的文件路径。渲染前校验数据，覆盖检查另运行 `check_coverage.py --module-dir 模块目录`。
