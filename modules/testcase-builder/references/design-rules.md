# 设计规则

读取 [公共数据契约](../../req-processor/references/data-contract.md) 后，以原文、需求规范、REQ/AC 和相关附图设计用例。工作簿格式见 [case-template.md](case-template.md)。

## 先确定可设计范围

正式入口需要模块的 `需求规范.md` 与 `REQ清单.json`，并通过上游 `validate_spec.py --module-dir`。这保证结构与证据引用有效，不代替阅读。需求被 P0 未决问题阻塞时，仅排除对应 blocked 范围；其他 active 要求继续。没有 active 要求时不生成正式用例，也不报 100%。

已有拆分报告或跨模块信息应一起读取；模块缩写以 REQ 清单和拆分记录的一致值为准。不创建与当前规则无关的端到端、权限或非功能要求。

上游资料缺失时，在当前任务包含需求整理的情况下先用 `req-processor` 补齐。用户明确要求“直接给草稿”时可基于可读原文设计并使用 `--draft`，注明依据、未确认规则和缺少的关联覆盖检查；不能将其描述为正式已核验用例。

## 从可观察规则到场景

对每条 active REQ 及每个 AC，找出触发条件、输入/状态、操作和可见结果，再选代表性用例。原文没有规定的结果列待确认事项，而不是写进正式预期。

| 场景 | 何时适用 | 设计重点 |
| --- | --- | --- |
| 正常 | 有已确认成功路径 | 最短完整路径及业务结果 |
| 备选 | 原文明确提供另一合法路径 | 与正常流不同的选择或取消结果 |
| 异常 | 原文明确非法输入或失败规则 | 错误处理与不应发生的业务变化 |
| 边界 | 有明确范围、长度、数量、精度 | 临界点、刚内、刚外；单位一致 |
| 非功能 | 有明确指标或约束 | 可测条件、观测方法和阈值 |
| 端到端 | 材料明确跨模块协作 | 上游输入如何反映到下游可见结果 |

不要为了凑齐三流添加“取消”“网络失败”“无权限”等未规定规则。备选流未规定可以评为不适用并记录理由；确有规则但未设计则是缺失。附图只有布局时也不能自动推导业务行为。

## 跨 REQ 与跨模块的关联写法

`关联需求` 表明“这条用例验证了哪些需求”，不是“这条用例经过了哪些页面”。按协作发生在哪里分两种写法，不要混用：

| 协作范围 | `关联需求` | 表达方式 |
| --- | --- | --- |
| 模块内两条及以上 REQ 共同决定结果 | 列出全部相关 active REQ | 每个被验证的 AC 必须分别属于所列 REQ |
| 对端 REQ 不在本模块 REQ 清单（跨模块） | 只挂本模块的 REQ | 置 `场景类型=端到端`，预期结果写清上游输入与下游可见结果两侧观察点 |

跨模块协作**不挂对端模块的 REQ 编号**：本模块 REQ 清单里没有它，校验会判定为未知需求，所列 AC 也无法归属。对端行为要到对端模块自己的用例集里登记；确需跨模块追溯时，在两份交付里互相引用用例编号。

同时关联多条 REQ 只是结论，不能靠改关联凑数：多挂一条 REQ 必须同时补上只有两侧都正确才成立的结果与观察点，否则仍算单 REQ 用例。多个互不相关规则不合并进一条用例。

## 按规则选择方法

- 场景法：有步骤与结果的用户路径。正常保存至少验证成功提示与业务状态，若这两者均为原文要求。
- 等价类：输入可分为有效/无效集合。每个有区别的已确认类有代表值，避免同类重复堆砌。
- 边界值：原文给出范围或精度。如“价格大于0、最多2位小数”，可用 `0`、负数、`0.01` 和 `0.001`；不能假定上限、是否允许科学计数法或具体舍入方式。
- 错误推测：有业务证据支持的易错情形。推测测试风险可以提出，但未确认的处理规则不进入正式预期。
- 判定表：多个已确认条件共同决定结果时，列出有业务差异的组合。
- 状态迁移：有明确状态与合法/非法转换时覆盖转换，不从按钮外观猜状态机。

不强制每个模块用齐六种方法；在评审中为所有方法记录适用性、证据或原因。`场景类型` 标记用例主要场景，`设计方法` 可有多项且必须反映实际设计。

## 可执行内容

前置条件写明角色、页面与初始业务状态；不擅自新增权限规则。测试数据写具体值或明确生成方式，步骤用单一、可定位的动作，预期用页面文案、列表记录、状态或可验证数据表达。准备数据和清理建议不能冒充业务要求。

写法受四条硬约束，违反即按 [字段写法](case-template.md#字段写法) 改写：

1. **不重复公共段**。测试环境、账号约定、取证方式写在 `module_preconditions` / `evidence_setup`，前置条件只留本条独有状态。同一句在模块内出现两次以上即视为重复。
2. **不把审计信息写进业务字段**。前置条件描述业务状态（"A 处于禁言状态"），不写"已核实""已确认"；能力是否核对由 `automation_evidence` 表达，准备缺口由 `preparation` 表达。
3. **不用项目内部标识符作描述语言**。必须出现时按 [字段写法](case-template.md#字段写法) 的术语要求给出中文说法或加解释。
4. **不写未完成的句子**。缺失的能力、接口或时钟，写清缺什么、怎么补，或移入 `preparation`，不在前置条件里留半句。

预期结果必须落到具体观察对象；写不出落点的预期（"功能正常""符合预期"）按无预期处理，不得作为通过依据。设计与渲染后运行 `case_readability.py --module-dir 模块目录` 自查可读性。

一条用例可以验证同一流程中的多个 AC，但要明确每个结果如何观察。多个互不相关规则不混在一条难以判断失败原因的用例中。只有真正验证某条 AC 时才关联它；单纯走到相关页面不算覆盖。

优先级 P0 用于核心业务或重大数据风险，P1 用于重要分支和输入校验，P2 用于低风险展示/细节，结合用户项目约定调整。自动化标“是”应有稳定可观察条件；需要人工主观判断时标“否”；缺少环境或可定位信息时标“待定”并在评审提出确认建议。首版不生成或录制自动化脚本。

设计完成后保存 JSON，运行 render 与双覆盖检查。REQ、AC 关联均 100% 仍需评审边界、异常和流程充分性；补完关联不能靠把所有编号机械挂到一条用例。
